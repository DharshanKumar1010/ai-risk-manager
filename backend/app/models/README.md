# RiskIQ model layers

One file per architecture layer, never merged. This README carries each layer's measured
result, the baselines that lost, and — required by
`.claude/skills/ml-evaluation-standards/SKILL.md` section 4 — an explicit
**"What this does NOT catch"** section written from false negatives actually observed rather
than imagined.

Numbers here are regenerated by the training scripts. The full, current report lives in
[`notebooks/tier1_report.md`](../../../notebooks/tier1_report.md); this file is the summary
and the interpretation.

---

## Tier-1 — real-time per-transaction anomaly scoring

`tier1_anomaly.py` (scoring), `tier1_features.py` (input definition),
`train_tier1.py` (training and comparison).

### What Tier-1 is allowed to see

Tier-1 must be scoreable at ingestion with no dependency on Tier-2 or Tier-3. That constraint
sorts the available columns into four classes — worked out in `tier1_features.py`:

| class | what it needs | examples |
|---|---|---|
| **A — row-only** | the arriving transaction alone | `amount_log`, `hour_of_day`, `has_identity`, `freq_*` (dict lookup), and every raw IEEE-CIS column: `C1`-`C14`, `D1`-`D15`, `M1`-`M9`, card/address/distance, the identity sidecar |
| **B — account state** | one indexed range scan | `velocity_{count,sum}_{1h,24h,7d}`, `amount_zscore_vs_own_history`, `device_*`/`addr_*` familiarity, `counterparty_prior_txn_count` |
| **A′ — post-settlement** | the settled balance (PaySim only) | `balance_error_orig`, `balance_error_dest`, `drains_origin_balance`, `newbalance*` |
| **C — excluded** | another tier's output | Tier-2 reconstruction error, Tier-3 ring scores |

Class B is included. Those are Phase 1 **feature-store** outputs, not Tier-2/3 model outputs,
so using them leaves Tier-1 independently scoreable — which is what the constraint asks.

Class A′ is excluded from the deployable PaySim model and reported separately, because a real
ingestion-time scorer does not yet know the balance a transaction settles to.

**Tier-1 mints its own `feature_version`**, distinct from the Phase 1 pipeline's. Tier-1 reads
the raw row columns the pipeline deliberately kept out of `transactions.features` — chiefly
`C1`-`C14` and `D1`-`D15`, Vesta's own precomputed per-entity aggregates, which are the
strongest signal IEEE-CIS carries. Its input set is genuinely a different definition, so
reusing the pipeline's hash would be a false claim about what produced a prediction.

**Denied outright**, enforced by `tests/test_tier1.py`: labels, split metadata, identifiers,
and anything monotone in time (`TransactionDT`, `TransactionID`, PaySim's `step`). Under a
chronological split every test value of those exceeds every train value, so a tree splits on
them, scores superbly in-sample and has learned nothing. That is the single most likely way
this phase could have produced a fake result.

### Results — IEEE-CIS, held-out test (n=88,581, positives=3,083, base rate 3.4804%)

| candidate | PR-AUC | 95% CI | lift | precision | recall |
|---|---|---|---|---|---|
| _no-skill floor (random ranker)_ | 0.0348 | — | 1.0x | — | — |
| amount-only ranking | 0.0371 | 0.0356–0.0391 | 1.1x | 0.034 | 0.502 |
| **IsolationForest** (unsupervised) | 0.0886 | 0.0847–0.0930 | 2.5x | 0.044 | 0.853 |
| **LightGBM** (matched inputs) | 0.5119 | 0.4955–0.5303 | 14.7x | 0.105 | 0.878 |
| **LightGBM** (full inputs) — *selected* | 0.5276 | 0.5117–0.5462 | 15.2x | 0.106 | 0.877 |

Two comparisons, and the second is the interesting one:

- **Supervision is worth almost everything.** IsolationForest 0.0886 → matched LightGBM 0.5119
  on *the identical matrix*, a paired delta of 95% CI [0.4241, 0.4558]. That is why the matched
  candidate exists: without it, "LightGBM won" would confound supervision with richer inputs.
- **Native categoricals are worth a little, and it is real.** Matched 0.5119 → full 0.5276,
  paired delta 95% CI **[0.0105, 0.0211]** — excludes zero, so the selection is justified.

  Worth noting *why* that needs the paired test: the two models' marginal intervals
  (0.4955–0.5303 and 0.5117–0.5462) overlap substantially, which looks like a tie and is not
  one. Both models are scored on the same test split, so their errors are correlated; pairing
  each bootstrap resample across both models removes the split's shared variance and leaves
  only the difference between the models. Reading overlapping marginal intervals as "no
  significant difference" is a standard error, and it would have been made here.

**The deployable operating point.** The cost-minimising threshold flags 28.9% of traffic, which
assumes an unbounded review queue. Capped at 1% of traffic instead:

```
Threshold: 0.813710  (chosen on validation by flagging at most 1.0% of validation traffic)
Precision  0.8734      Recall  0.2462      F1  0.3841

Confusion matrix        Predicted
                     neg        pos
Actual  neg        85,388        110
        pos         2,324        759
```

87% of what a reviewer opens is genuine fraud, at 0.98% of traffic reviewed. That is the
number to quote for a product; the 0.5276 PR-AUC is the number to quote for the model.

The realised 0.98% lands under the 1% ceiling because the threshold is chosen on validation
and IEEE-CIS's base rate is near-stationary across splits (3.52% / 3.43% / 3.48%). It does
**not** transfer on PaySim, where the same procedure overshoots to 2.25% because that corpus's
test window runs at 7x its validation base rate — the non-stationarity Phase 1 measured and
flagged. A capacity ceiling fitted on validation is only a ceiling while the base rate holds,
which is worth knowing before Phase 7 sizes a review queue from one.

**Latency**: p50 5.62ms, p95 6.38ms, p99 6.86ms over 100 sequential `score()` calls — inside
the 50ms budget by roughly 8x. Measures the scoring call only; feature assembly is Phase 7's.
(PR-AUC reproduces to four decimals across runs; latency is wall-clock and moves by ~1ms
between them, so treat the budget headroom rather than the digits as the result.)

Getting there took one real optimisation. The obvious implementation — assemble a one-row
`DataFrame` and hand it to LightGBM — cost 21.6ms per call: ~17.9ms building 28
`pd.Categorical` columns and ~9.2ms while LightGBM re-derived the category mapping. Serving now
converts categoricals to integer codes and scores a plain float array, which is the same
representation LightGBM built internally at training time. Predictions are identical to the
batch path (verified to 0.0 difference, and asserted by
`test_numpy_and_pandas_paths_agree`) and the call is ~200x faster.

### Results — PaySim: a near-perfect score that should not be believed

PaySim's selected model scores **PR-AUC 0.9998**, and the ingestion-safe variant still scores
0.9386. Under ml-evaluation-standards section 4 that is a leak signal, not a triumph, so it was
investigated before being reported. **The cause is a deterministic artefact of the simulator:**

| measured on the test split | value |
|---|---|
| `amount == oldbalanceOrg` (exact, ±0.01) given **fraud** | 97.49% (3,919 / 4,020) |
| `amount == oldbalanceOrg` given **legitimate** | **0.00%** (0 / 412,277) |
| precision of that single rule, alone | **1.0000** |
| average precision of `-\|amount − oldbalanceOrg\|` as a lone score | **0.9751** |

PaySim's fraud agent takes over an account and transfers *exactly* the full balance. No
legitimate transaction in 412,277 does that. So one two-column comparison — both columns
available at ingestion — reproduces almost the entire result.

This is **not** a leak in our pipeline: no future information is read, the split boundaries
hold, and the encoders are fitted on train alone. It is a property of the corpus. Three
consequences, all of which bind on later phases:

1. **PaySim's Tier-1 PR-AUC is not evidence of fraud-detection capability.** It measures the
   simulator's fraud generator having a deterministic signature. It is reported because
   suppressing it would be worse, and it is never quoted as a headline.
2. **IEEE-CIS carries the Tier-1 headline.** Its 0.5276 is a real measurement against real
   card fraud with no such tell.
3. **Phase 5 must not train the meta-learner to trust Tier-1 on PaySim.** A fusion model
   fitted there would learn "Tier-1 is always right", which transfers nowhere. PaySim's value
   to this project is its *graph structure* for Tier-3, not its Tier-1 separability.

A fourth, smaller consequence: PaySim's two LightGBM candidates both reach validation PR-AUC
1.0000, so the validation-based selection is choosing between models that are indistinguishable
on the criterion. It picks matched inputs, and the paired test-split delta against full inputs
is 95% CI [-0.0002, -0.0000] — the "winner" is fractionally *worse* on test. That is the
correct and honest outcome of not letting test choose, and it is a further reason the PaySim
entry is registered rather than deployed.

On how it was found, and the limit of the automated guard. The `PR-AUC > 0.95` warning fired
automatically. The per-feature gain table then pointed at the right place — `oldbalanceOrg`
28.0%, `newbalanceOrig` 22.9%, `transaction_type` 21.4% — but it could not state the finding,
because the tell is a *relation between* two columns rather than the influence of either. No
single PaySim feature exceeds 0.47 average precision on its own; `-|amount − oldbalanceOrg|`
reaches 0.9751. The relation was found by hand. An automated per-feature scan would have
flagged the neighbourhood and missed the mechanism, which is worth knowing before relying on
one in a later phase.

### What this does NOT catch

Written from false negatives actually observed on the IEEE-CIS test split, at the
capacity-constrained operating point (759 caught, 2,324 missed).

- **Expensive fraud, disproportionately.** This is the most important qualification of the
  headline, and it is the opposite of what the cost model's shape would lead you to assume.
  Recall falls as the amount rises:

  | fraud amount quartile | range | frauds | recall |
  |---|---|---|---|
  | Q1 | 2.23 – 33.20 | 768 | **0.3945** |
  | Q2 | 33.20 – 63.95 | 773 | 0.1979 |
  | Q3 | 63.95 – 150.00 | 761 | 0.2208 |
  | Q4 | 150.00 – 3,133.06 | 781 | **0.1729** |

  Median amount of caught fraud is 43.65; of missed fraud, 75.00. Stated as the number that
  actually matters: the model catches **24.6% of fraud by count but only 14.6% by value**
  (68,759 caught of 469,609 total fraud value). Anyone quoting the recall figure without this
  is overstating what the layer recovers.

  The cause is that the cost model chooses only the *threshold*; the model's *ranking* is
  fitted on the label and is value-blind. Cost-sensitive learning is the obvious lever and it
  belongs to Phase 6, where the causal cost layer can weight training directly.
- **Fraud on accounts with no history — mildly.** 57.7% of IEEE-CIS accounts hold a single
  transaction (20.0% of rows), and for those every class-B feature is null or degenerate.
  Measured, the penalty is real but small: recall 0.2252 on accounts with no prior history
  against 0.2509 on accounts with some. Less than the structural argument would predict,
  because the class-A `C`/`D` blocks carry per-entity history of their own.
- **Slow-building account takeover.** Tier-1 sees one transaction. A takeover that escalates
  over days looks unremarkable transaction-by-transaction. **This is precisely what Tier-2's
  sequence model is for**, and the gap is by design rather than a defect.
- **Coordinated rings.** Likewise invisible: a ring of individually-plausible transactions
  across many accounts has no per-transaction signature. **Tier-3's job.**
- **Anything relying on a category unseen in training.** New device strings, new email domains
  and new card types frequency-encode to 0.0 and unseen native categories map to LightGBM's
  missing branch. That is the honest encoding of "unknown", but it means a genuinely novel
  attack surface is scored on weaker evidence than an established one.
- **Recall at any staffable threshold is 24.6%.** Three quarters of fraud passes the 1%-flag
  operating point. Tier-1 is a first filter, not a detector — which is the architectural
  premise of having Tiers 2, 3 and a meta-learner at all.

### Baselines kept, not discarded

**IsolationForest (PR-AUC 0.0886, 2.5x the floor)** lost decisively and is retained
deliberately. Chargeback labels arrive weeks after the transaction, so the unsupervised floor
is the honest answer to "what can we score for a merchant with no labelled history yet?" —
a real cold-start condition, not a hypothetical. It is the fallback when supervision is
unavailable, and it is the reference that makes the supervised number interpretable.

**amount-only ranking (PR-AUC 0.0371, 1.1x the floor)** is the reference every model must beat
to justify its complexity. It barely clears random on IEEE-CIS, which is itself informative:
amount alone is not a fraud detector on this corpus.

### Reproducibility

Seed 42, set and logged. LightGBM runs with `deterministic=True`, `force_row_wise=True` and a
fixed `num_threads` — without those, multithreaded histogram construction varies between runs
and the registry's reproducibility claim would be false. Every trained model appends to
[`models/registry.json`](../../../models/registry.json) with its algorithm, training window,
`feature_version`, hyperparameters, seed, held-out metrics, cost estimate and losing baselines.

### Designed for, not implemented

`OnlineRecalibrator` in `tier1_anomaly.py` is an interface stub. Fraud models drift and a
threshold chosen on one validation window stops being cost-minimising; the intended shape is
that confirmed outcomes shift the operating threshold without refitting. Deliberately not
built in Phase 2 — recalibrating against live outcomes needs a labelled feedback path that
does not exist in this project (Phase 9's webhook records only this service's own decision,
never a confirmed outcome, so it did not supply this despite an earlier version of this note
promising it would), and building it now would mean building it against imagined data.

## Meta-learner — XGBoost fusion (Phase 5)

`meta_learner.py` fits the layer; `meta_features.py` builds its matrix and owns the leakage
discipline; `train_meta_learner.py` runs the experiment.

**This layer loses to Tier-1 on the project's headline metric and is not recommended for
serving.** It is kept because the experiment it embodies is the deliverable: Phases 3 and 4 both
deferred "does this layer pay for itself?" to here, and answering it required building the fusion.

### Results — IEEE-CIS, held-out test (n=88,581, positives=3,083, base rate 3.4804%)

Threshold 0.6035, chosen on the V-late validation slice by minimising estimated cost under a 1%
review-capacity cap; it realises 1.07% on test. The model scores with three trees — early stopping
selected iteration 2 on V-fit, and scoring honours that selection.

```
PR-AUC     0.4954  (95% CI 0.4791-0.5141)
           no-skill floor 0.0348 (14.2x lift)
Precision  0.8282      Recall  0.2549      F1  0.3899

Confusion matrix        Predicted
                     neg        pos
Actual  neg     85,335        163
        pos      2,297        786
```

False-positive cost estimate 4,711 per 1,000 transactions, under the assumptions `app/ml/cost.py`
states in full. Against Tier-1 alone on the same split (0.5276): **paired delta -0.0322, 95% CI
[-0.0373, -0.0273]**. The interval excludes zero on the negative side — not a tie.

### The cost comparison points the other way

PR-AUC is a ranking metric and the recommendation has to be justified by cost. At a matched 1% flag
rate — **both cuts are quantiles of the test score vectors**, which is what makes the flag rates
comparable, and the table is computed only after the shipped thresholds were fixed on validation:

| model | flag rate | precision | recall (count) | recall (**value**) | cost per 1,000 |
|---|---:|---:|---:|---:|---:|
| meta-learner | 0.94% | 0.8257 | 0.2228 | **0.1689** | **4,817.97** |
| Tier-1 alone | 1.00% | 0.8646 | 0.2485 | 0.1500 | 4,903.53 |

The fusion catches **less fraud by count and more by value**, making it ~1.7% cheaper under this
project's cost model. That is a bare point estimate — there is no bootstrap for a cost difference
here — and it rests on that model's stated assumptions. Not grounds to ship; too specific to
discard. Phase 6 should re-run the comparison with its own cost layer.

### Why it loses — and what was not established

The meta-learner must be fitted on *out-of-sample* Tier-1 scores, which requires forward-chaining
folds, and fold models are weaker than the full-train model that serves:

| fold | train rows | validation PR-AUC |
|---|---:|---:|
| 2 | 82,675 | 0.4200 |
| 3 | 165,351 | 0.4587 |
| 4 | 248,026 | 0.4776 |
| 5 | 330,702 | 0.5202 |
| full-train | 413,378 | **0.6155** |

So it was fitted against a Tier-1 column worth 0.42-0.52 and applied to one worth 0.6155, and the
fold-5-to-full-train jump exceeds what 25% more data explains — recency, not volume.

**That is not established as the cause.** Early stopping selected **iteration 2**: the shipped model
is three trees. A validation metric peaking that early is consistent with the ablation, but it means
the loss is confounded between the handicap and simply not fitting. The discriminating diagnostic —
refit on the in-sample Tier-1 column, compare on the arbiter slice — was not run.

### Calibration

Platt scaling on the margin. **Test Brier 0.0233, ECE 0.0037** against a 3.4804% base rate, across
10 populated bins: 83,918 rows predicted 0.0141 against 0.0151 observed, 1,674 predicted 0.1543
against 0.1553. Probabilities span 0.0093 to 0.9972, median clean row 0.0099. These are usable as
probabilities, not only as a ranking.

Isotonic is the documented alternative at ECE 0.0022 — 1.7x better, the small gap expected between a
flexible calibrator and a two-parameter one. The sigmoid ships because it is strictly monotone and
leaves PR-AUC exactly intact, whereas isotonic ties scores and moves the headline metric by an
artefact of step width. If a downstream consumer needs the last of the calibration accuracy more
than it needs the ranking, that trade should be revisited rather than assumed.

### What this does NOT catch

From the 2,297 false negatives actually observed at the shipped operating point. **These figures were computed by hand against the shipped model and are not regenerated by the training run** — there is no false-negative profiler for this layer, unlike Tiers 2 and 3, so they will go stale if the model is retrained:

- **Four-fifths of fraud value walks past it.** Recall 0.2549 by count but **0.1859 by value**;
  81.4% of test fraud value sits in transactions it did not flag. Missed fraud has a *higher* median
  amount than caught fraud (75.00 against 50.00), so the misses are not the cheap tail.
- **Recall by fraud-amount quartile**: 0.3737 (cheapest), 0.2083, 0.2260, 0.2125. It is weakest on
  ordinary mid-to-high-value transactions.
- **It catches nothing Tier-1 does not.** The ablation put Tier-1's leave-one-out contribution at
  +0.4263 and the engineered passthrough at +0.0048 with an interval spanning zero.
- **Ring-only and sequence-only fraud remain uncaught.** Tier-2 and both Tier-3 blocks were retired,
  so an account whose only signal is coordinated ring structure or an anomalous behavioural sequence
  is invisible here, exactly as it is to Tier-1.
- **Its explanations restate one feature.** Across ten read samples, `tier1_score` was the top
  contributor every time, an order of magnitude above everything else. For a reviewer that points
  back at `tier1_anomaly.explain` rather than adding anything.

### Baselines kept, not discarded

- **Tier-1 alone** — 0.5276 on PR-AUC, thresholded on validation at 0.813710 (Phase 2's registered
  capacity point). It wins the headline and is what Phase 6 should consume.
- **Isotonic calibration** — better calibrated, but it ties scores and costs PR-AUC.
- **Every ablation variant** — in the registry entry's `baseline_comparison` and
  `ablation_validation` blocks.

### Explanations

TreeSHAP via XGBoost's native `pred_contribs=True`, not the `shap` package — the same algorithm,
verified bit-identical (max absolute difference 0.0), and it avoids an import that fails this repo's
`filterwarnings = ["error"]` configuration. Contributions are in margin space; the calibrator is
strictly monotone, so they explain the shipped probability's ordering.

**`top_features` is an evasion oracle.** It tells the recipient which signals drove a decision, which
is what an adversary needs to avoid triggering them. `MetaResult.public()` exists so that omitting it
from a response is the default a caller must *undo* rather than remember; `predict(..., explain=False)`
skips computing it entirely. `AuditRecord.top_features` records it in the audit trail, which is a
different thing from returning it in a response.

### Reproducibility

Seed 42, logged. `python -m app.models.train_meta_learner`. Upstream models pinned by id rather than
resolved by "latest" — Tier-3 has sixteen registry entries and picking one by accident is a documented
Phase 4 hazard. Artefacts are XGBoost JSON plus a plain-JSON sidecar carrying the selected iteration
and the two calibrator parameters; nothing in the load path unpickles.

## Causal cost layer — cost-aware decisioning (Phase 6)

`causal_cost.py` + `ml/ope.py`. Consumes Tier-1's score, Platt-recalibrated on V-fit; every threshold
chosen on V-late. Ships a `plug_in` policy that ranks by **expected cost saving** rather than by
probability.

### There is no treatment variable, and that determines what this layer is

The phase brief asked for IPW on historical actions. Neither corpus records one: IEEE-CIS has no
decision/decline/review/dispute column across its 394 + 41 columns, and PaySim's `isFlaggedFraud` is a
deterministic simulator rule firing on 16 of 6.36M rows, nested inside the label, already dropped by
the pipeline. Every transaction here was allowed. **No causal effect is recovered and none is claimed.**

What follows is provable rather than regrettable. Under the stated cost model both potential outcomes
are deterministic given `(label, amount)`, so

```
tau(x) = (1 - p(x)) * r  -  p(x) * (A + f)
```

has every term either known at decision time or equal to `p(x)`. **The DR-Learner collapses exactly
onto a cost-weighted plug-in.** Two consequences, both measured: the break-even threshold becomes
per-transaction (`p > r/(A+f+r)`), and the only place learning could still help is regressing realised
loss directly — which `learned_loss` does, and which the run tests rather than assumes.

The DR machinery is kept for **off-policy evaluation against a simulated logging policy**, where the
true policy cost is exactly computable and the estimators can be validated rather than trusted.

### Results — IEEE-CIS, held-out test (n=88,581, positives=3,083, base rate 3.4804%)

All three policies rank the same calibrated probability, matched to a 1% flag rate:

| policy | precision | recall (count) | recall (**value**) | cost per 1,000 |
|---|---:|---:|---:|---:|
| `probability` (Tier-1 baseline) | 0.8646 | 0.2485 | 0.1500 | 4,902.49 |
| **`plug_in`** (shipped) | 0.4955 | 0.1424 | **0.3698** | **3,804.02** |
| `learned_loss` | 0.5056 | 0.1453 | 0.3453 | 3,932.14 |

Paired bootstrap intervals, threshold re-derived inside each resample:

| comparison | cost delta / 1,000 | 95% CI | verdict |
|---|---:|---:|---|
| `plug_in` vs `probability` | −1,098.48 (**−22.41%**) | [−1,345.28, −881.81] | cheaper, excludes zero |
| `learned_loss` vs `probability` | −970.35 (−19.79%) | [−1,189.92, −769.45] | cheaper, excludes zero |
| `learned_loss` vs `plug_in` | +128.13 (+3.37%) | [−30.41, +300.03] | **TIE** |

Two findings, and the second is the more interesting one.

**Cost-aware ranking wins by a large margin — though note what the comparison does and does not
establish.** At a fixed flag budget, ranking by `tau(x)` is the Bayes-optimal selection for exactly the
cost function used to score it, given a calibrated `p`. So this measures *how large* the gain is on this
corpus and *whether the calibration holds* (ECE 0.0057 says it does) — not *whether* cost-aware ranking
works, which the collapse proof already settles. Count recall *falls* by 43% while value recall rises by
147%: it is not detecting more fraud, it is detecting more expensive fraud. That mechanism is also the evidence it is not a leak: PR-AUC drops to
0.3194, nowhere near the 0.95 suspicion wire.

**Cost-sensitive *training* buys nothing over cost-sensitive *thresholding*.** `learned_loss` ties the
plug-in — the interval includes zero and its point estimate is on the wrong side. This is the question
`BUILD_LOG` handed the phase, and the answer is what the collapse proof predicts: given a calibrated
probability, the plug-in is already the right combination, and fitting a second model to reach it adds
estimation error without adding information.

### The headline is regime-dependent — read this before quoting 22%

The advantage falls to **−2.22%**, CI [−582.18, −145.50] per 1,000, under a card-not-present cost
model (FP 50, FN amount+500). Note what that says and does not say: the interval still excludes zero,
so cost-aware ranking is *genuinely* cheaper under CNP pricing too — but the effect is an order of
magnitude smaller, and the same pre-registered tie rule is applied to this number as to the headline
rather than only to the one that flatters the phase.

The mechanism is arithmetic. Value-weighting can only exploit the share of false-negative cost that
*varies* between transactions. At a 15.00 fee against a median test amount of 68.50 that share is
82.0%; at a 500.00 fee it is 12.0% — the flat fee dominates, every miss costs roughly the same, and
cost ranking collapses most of the way back toward probability ranking.

So the honest claim is conditional: **cost-aware ranking pays in proportion to how heterogeneous the
loss is.** Which regime a payments business is in is a question about its own chargeback economics,
not something this corpus answers.

### Is the cost advantage circular?

The obvious objection: if the policy ranks by `p·(A+f)` and fraud correlates with amount on this
corpus, is it just re-using the amount as a hidden risk signal? Worth answering plainly.

Amount reaches every model here as the engineered `amount_log`, which **is** a live Tier-1 feature —
the raw `amount` and `TransactionAmt` columns sit on the deny list only because they are exact
duplicates of it, monotone and so giving a tree identical splits. Nothing is withheld and nothing is
smuggled in. It is not leakage, because the amount is known before the decision is made, which is
precisely what makes it usable in the cost arithmetic at all.

The decisive evidence is the direction of the metrics: count recall **falls** 0.2485 → 0.1424. A
policy exploiting amount as a hidden risk signal would catch *more* fraud, not less. This one catches
fewer frauds and more money, which is exactly what the cost function asked for.

### Calibration

Expected calibration error 0.005725, Brier 0.022601, on test. This matters more here than in Phase 5:
every figure this layer emits is a probability multiplied by an amount, so calibration error
propagates directly into cost and moves every break-even threshold with it.

### Off-policy estimator validation

Against a **simulated** logging policy whose propensity is known by construction, with truth computed
exactly from the labels. On the shipped policy: direct method −8.66% bias, IPW +2.19%, doubly robust
+1.35%. Read carefully — a correct propensity makes IPW unbiased by construction, so this establishes
that the estimators are implemented correctly and recover a known answer. It cannot establish which
would win where the propensity must be estimated, which is the case that matters in deployment and is
not testable on data with no logged actions at all.

### What this does NOT catch

From the false negatives actually observed at the shipped operating point, and regenerated by the run
— unlike the Phase 5 section above, which was computed by hand and goes stale on retraining:

- **High-value fraud that Tier-1 scores as ordinary.** The five costliest misses carry amounts from
  3,076.97 down to 1,504.47 at probabilities of 0.0108, 0.0226, 0.0268, 0.0096 and 0.0041 — every one
  of them an order of magnitude below the ~0.035 median break-even. Even multiplied by a large amount,
  a probability that low does not clear the bar. Value weighting reprioritises what Tier-1 already
  suspects; it cannot rescue what Tier-1 scored as clean. Note the second pattern in those rows: three
  of the five come from accounts with an established history (2, 2 and 12 prior transactions) and no
  new device or address, so the signals Tier-1 leans on are all absent.
- **It improves no detection whatever.** Every policy reads the same Tier-1 probability. This layer
  changes which flagged transactions are worth a queue slot, and nothing else.
- **It spends count recall to buy value recall.** Recall falls 0.2485 → 0.1424 on 3,083 positives:
  true positives drop 766 → 439, so **327 more frauds per 88,581 transactions get through**. They are
  the cheap ones, and that is the trade the cost function asked for — but it is the largest single
  downside of the shipped policy, and a business with a regulatory or reputational *count* target
  rather than a loss target should not ship this.
- **Its advantage shrinks as the chargeback fee dominates the amount** — see the regime section above.
- **It prices `review` and `block` identically.** Both put a transaction in front of a human, but a
  hard decline damages a customer relationship in a way a review does not, and this model cannot see
  the difference.
- **Review capacity is a hard count cap and cost is linear in mistakes.** No queue congestion, no
  churn from repeated false declines, no recovery on disputed fraud. All three would raise the true
  cost of a false positive.

### Baselines kept, not discarded

- **`probability` ranking** — Tier-1's own behaviour, PR-AUC 0.5276, cost 4,902.49 per 1,000. It wins
  every count-based metric and loses on cost.
- **`learned_loss`** — a LightGBM Tweedie regression on realised loss over Tier-1's exact feature set.
  Ties the plug-in; not shipped. Its reported figures come from a single train-fitted booster scoring
  test, which is correct; a five-block forward-chaining out-of-fold column is also computed but is only
  a coverage diagnostic and feeds no reported number.
- **The unconstrained cost optimum** is reported beside the capacity-capped point, never instead of
  it: it flags 23.1% of traffic at 1,135.79 per 1,000, which no review queue could absorb.

### Reproducibility

Seed 42, logged. `python -m app.models.train_cost_learner`. The artefact is a plain-JSON sidecar
carrying the threshold, the cost model and its assumptions; the shipped `plug_in` policy holds no
booster, so nothing in its load path unpickles. One caveat: `LOSS_PARAMS` enables bagging and feature
sampling, both of which draw against row position, so a run is reproducible given the same parquet but
not invariant to a permutation of it.
